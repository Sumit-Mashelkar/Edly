# Peblo TV Mini (Edly)

This repository contains a V1 end-to-end media catalogue workflow with a FastAPI backend, PostgreSQL, a CMS, a viewer, and a publish pipeline.

## Local Windows Setup

The commands below run the backend, CMS, and viewer without Docker. PostgreSQL 16 must be installed and running as the `postgresql-x64-16` Windows service.

Prerequisites: Python 3.9+, Node.js/npm, and PostgreSQL 16.

If the repository virtual environment does not exist yet, create it from the repository root:

```powershell
cd D:\local-Edly\Edly
py -3 -m venv .venv
```

### 1. Configure PostgreSQL

Create the application role and database using the PostgreSQL admin password chosen during installation:

```powershell
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -U postgres -h localhost -d postgres
```

Then run in the `psql` prompt:

```sql
CREATE USER peblo WITH PASSWORD 'peblo';
CREATE DATABASE peblo OWNER peblo;
\q
```

If the role or database already exists, use:

```sql
ALTER USER peblo WITH PASSWORD 'peblo';
ALTER DATABASE peblo OWNER TO peblo;
\q
```

### 2. Initialize the backend database

Open a PowerShell terminal in the repository and run:

```powershell
cd D:\local-Edly\Edly\backend
$python = "D:\local-Edly\Edly\.venv\Scripts\python.exe"

# Local PostgreSQL uses localhost. The Docker value uses the hostname db.
$env:DATABASE_URL = "postgresql+psycopg://peblo:peblo@localhost:5432/peblo"

& $python -m pip install -r requirements.txt
& $python -m alembic upgrade head
& $python -m app.db.seed
```

The seed command creates the development users:

- `editor@example.com` / `peblo-dev-password`
- `admin@example.com` / `peblo-dev-password`

### 3. Start the backend

Keep the backend terminal open:

```powershell
& $python -m uvicorn app.main:app --app-dir "D:\local-Edly\Edly\backend" --reload --host 0.0.0.0 --port 8000
```

### 4. Start the CMS

Open a second PowerShell terminal:

```powershell
cd D:\local-Edly\Edly\cms
npm install
npx vite --host 0.0.0.0 --port 5173
```

### 5. Start the viewer

Open a third PowerShell terminal:

```powershell
cd D:\local-Edly\Edly\viewer
npm install
npx vite --host 0.0.0.0 --port 5174
```

Open the applications:

- CMS: `http://localhost:5173`
- Viewer: `http://localhost:5174`
- API health: `http://localhost:8000/health`

The health response should report `"database": "connected"` before signing in to the CMS.

### Docker setup

If Docker Desktop is available, the complete stack can also be started with:

```powershell
docker compose up --build
```

### Troubleshooting

- `connection timeout` on port `5432`: start the PostgreSQL Windows service.
- `password authentication failed for user "peblo"`: reset the `peblo` role password to `peblo` using `psql`.
- `No module named app`: start Uvicorn with `--app-dir "D:\local-Edly\Edly\backend"` or run it from the `backend` directory.
- Vite uses another port: stop the existing Vite process or open the port printed in its terminal.

## Architecture

CMS -> FastAPI -> PostgreSQL -> publish job -> published catalogue -> viewer

The CMS is responsible for editing metadata and uploading artwork. The backend enforces auth and validation. Publishing writes a complete catalogue JSON to local storage atomically, then the viewer reads that file instead of calling admin endpoints.

## Decisions and trade-offs

### Atomic publishing

The backend validates the database before publishing and writes a temporary file to the storage directory before replacing the final catalogue path atomically. If the process dies mid-write, the last known valid catalogue is preserved and the new file is not partially visible to viewers.

### Storage abstraction

The V1 storage layer is intentionally minimal: `LocalStorageService` centralizes file IO. Replacing it with R2 would mean swapping the implementation behind the same interface without touching publishing or business logic.

### Search

The backend exposes catalogue search at `/catalog/search`, while the current viewer loads the published catalogue once and filters its in-memory result for a responsive V1 experience. The CMS sends search and content filters to the admin API. A larger catalogue would benefit from server-side full-text indexes or a search service.

### Pre-published catalogue

The viewer reads a JSON catalogue file generated by the backend rather than querying PostgreSQL directly. This keeps reads fast and avoids locking the admin data layer. The trade-off is that the viewer can only reflect the last successful publish.

### Validation

The seed data is intentionally imperfect, so the validation report surfaces blocking issues instead of silently fixing them. These include missing required metadata, invalid sections, missing durations, and missing artwork.

### What you skipped

This V1 intentionally avoids rollback versions, publish dry runs, detailed audit logs, or more advanced storage features. The core publishing flow is the priority.

## Operational note

A useful production alert would be: `catalogue file missing or publish failed` because it directly impacts the viewer and the business outcome.

## V1 Tradeoffs and Missing Components

- Local filesystem storage keeps setup simple, but it is not suitable for multi-instance production deployments.
- The viewer reads the last published JSON catalogue, so edits are not visible until publishing succeeds.
- Viewer search is performed in memory after loading the catalogue; large catalogues would need server-side search or indexing.
- Authentication uses development seed users and JWTs; production identity management, password reset, and audit logging are not included.
- Artwork replacement is supported, but CDN delivery, image transformations, and permanent object storage are not included.
- Rollbacks, draft previews, scheduled publishing, bulk editing, and advanced workflow approvals are outside this V1.
