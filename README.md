# Peblo TV Mini

This repository contains a V1 end-to-end media catalogue workflow with a FastAPI backend, PostgreSQL, a CMS, a viewer, and a publish pipeline.

## Setup

1. Copy `.env.example` to `.env` and adjust secrets as needed.
2. Start the stack:
   ```bash
   docker-compose up --build
   ```
3. The backend will run Alembic migrations and seed the database on startup.
4. Open the CMS at `http://localhost:5173` and the viewer at `http://localhost:5174`.
5. Use the seed users:
   - editor@example.com / peblo-dev-password
   - admin@example.com / peblo-dev-password

## Architecture

CMS -> FastAPI -> PostgreSQL -> publish job -> published catalogue -> viewer

The CMS is responsible for editing metadata and uploading artwork. The backend enforces auth and validation. Publishing writes a complete catalogue JSON to local storage atomically, then the viewer reads that file instead of calling admin endpoints.

## Decisions and trade-offs

### Atomic publishing
The backend validates the database before publishing and writes a temporary file to the storage directory before replacing the final catalogue path atomically. If the process dies mid-write, the last known valid catalogue is preserved and the new file is not partially visible to viewers.

### Storage abstraction
The V1 storage layer is intentionally minimal: `LocalStorageService` centralizes file IO. Replacing it with R2 would mean swapping the implementation behind the same interface without touching publishing or business logic.

### Search
Search in the published catalogue is simple and runs on the backend, not inside the browser. That makes the search endpoint a good fit for small/medium catalogue sizes. It stops scaling when the catalogue becomes large enough that full-text indexes or a search service are needed.

### Pre-published catalogue
The viewer reads a JSON catalogue file generated by the backend rather than querying PostgreSQL directly. This keeps reads fast and avoids locking the admin data layer. The trade-off is that the viewer can only reflect the last successful publish.

### Validation
The seed data is intentionally imperfect, so the validation report surfaces blocking issues instead of silently fixing them. These include missing required metadata, invalid sections, missing durations, and missing artwork.

### What you skipped
This V1 intentionally avoids rollback versions, publish dry runs, detailed audit logs, or more advanced storage features. The core publishing flow is the priority.

### AI usage
The build used AI assistance for scaffolding and validation support. The generated output was accepted where it matched the challenge requirements and modified where local project constraints required alignment.

### Time
- Project scaffold and repo setup: 1 hour
- Backend models and database work: 2 hours
- Publishing and validation logic: 3 hours
- Frontend shells and Docker/CI setup: 2 hours

## Operational note
A useful production alert would be: `catalogue file missing or publish failed` because it directly impacts the viewer and the business outcome.
